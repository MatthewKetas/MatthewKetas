# Personal Portfolio System Design

## 1. Purpose

This website is a personal engineering portfolio for Matthew Ketas.

Its purpose is to clearly communicate:

- who Matthew is as an engineer,
- what kinds of technical problems he enjoys solving,
- the projects and professional work he has completed,
- how he approaches design, implementation, testing, and debugging,
- and why he would be a strong candidate for embedded systems, hardware-adjacent software, systems software, or full-stack engineering roles.

The website should not present Matthew as only a web developer.

The primary positioning should be:

> A computer engineer who enjoys working close to the hardware, building reliable software, integrating systems, and solving practical engineering problems across the stack.

The site should show technical range while maintaining a clear identity centered on computer engineering, embedded systems, software reliability, hardware/software integration, and high-quality engineering work.

## 7. Visual Direction

Use an editorial engineering aesthetic.

The site should combine:

- strong typography,
- clear hierarchy,
- structured layouts,
- restrained technical details,
- generous spacing,
- and thoughtful project imagery.

The design should feel more like a polished engineering publication or product case study than a standard resume website.

### Typography

Typography should communicate precision and professionalism.

Use:

- a highly readable sans-serif for body content,
- a strong display font for headings,
- and optionally a restrained monospaced font for labels, metadata, technologies, measurements, or code-related elements.

Do not use a monospace font for all content.

Typography should create hierarchy without relying on excessive card containers.

### Color

Use a restrained color palette.

The palette may include:

- a neutral background,
- dark, readable text,
- one primary accent color,
- and one optional secondary technical accent.

Accent colors should be used intentionally for:

- project categories,
- interactive states,
- diagrams,
- links,
- and important metadata.

Maintain sufficient contrast.

Do not use color as the only way to communicate meaning.

### Motion

Motion should be subtle and purposeful.

Good uses of motion include:

- revealing system diagrams,
- showing data or signal flow,
- demonstrating project interactions,
- emphasizing relationships between components,
- and improving navigation feedback.

Avoid animation that exists only to impress.

Respect `prefers-reduced-motion`.

## 10. Project Case Study Structure

Each major project should be presented as an engineering case study.

Do not create project pages that are only:

- a screenshot,
- a paragraph,
- and a list of technologies.

Each case study should include the following sections.

### 10.1 Summary

Briefly explain:

- what the project is,
- why it exists,
- who used it,
- and Matthew’s responsibility.

### 10.2 Problem

Explain the engineering problem.

Include:

- requirements,
- constraints,
- expected behavior,
- performance expectations,
- hardware limitations,
- timing requirements,
- team constraints,
- or reliability concerns.

### 10.3 System Context

Show where the project fits within the larger system.

Use:

- architecture diagrams,
- data-flow diagrams,
- state diagrams,
- sequence diagrams,
- hardware/software boundaries,
- or component maps.

### 10.4 Matthew’s Contribution

Clearly distinguish Matthew’s work from the work of the full team.

Use direct language such as:

- I designed,
- I implemented,
- I tested,
- I debugged,
- I integrated,
- I documented,
- or I collaborated on.

Avoid taking credit for work that was completed by others.

### 10.5 Technical Decisions

Explain important decisions and tradeoffs.

Examples include:

- language or framework choice,
- communication protocol,
- database design,
- thread or process model,
- test strategy,
- hardware interface,
- caching approach,
- error-handling strategy,
- performance optimization,
- or component boundaries.

### 10.6 Challenges

Explain one or more meaningful technical challenges.

Show:

- what failed,
- how the issue was investigated,
- what evidence was collected,
- how the solution was selected,
- and what was learned.

This is more valuable than pretending every project went perfectly.

### 10.7 Verification

Describe how the project was validated.

Examples:

- unit tests,
- integration tests,
- hardware testing,
- simulation,
- profiling,
- static analysis,
- manual verification,
- automated test frameworks,
- test fixtures,
- or failure injection.

Testing should be treated as a first-class engineering concern.

### 10.8 Result

Describe the final outcome.

Use measurable results when available.

Never invent numbers or impact.

### 10.9 Reflection

Briefly explain:

- what Matthew learned,
- what he would improve,
- or how he would approach the system differently today.

## 16. Accessibility

The site should meet WCAG 2.2 AA where practical.

Requirements include:

- semantic HTML,
- correct heading order,
- keyboard-accessible navigation,
- visible focus indicators,
- descriptive link text,
- sufficient color contrast,
- alternative text for meaningful images,
- labels for form controls,
- reduced-motion support,
- and no essential hover-only interactions.

Animations should not interfere with navigation or reading.

Technical diagrams should include text descriptions when necessary.

---

## 17. Responsive Design

The site must be designed mobile-first.

Test at minimum:

- small mobile,
- large mobile,
- tablet,
- laptop,
- desktop,
- and wide desktop.

Project diagrams must remain understandable on small screens.

Complex diagrams may:

- stack vertically,
- scroll horizontally within a labeled region,
- or provide a simplified mobile version.

Avoid shrinking diagrams until they become unreadable.

Navigation should remain simple and accessible.

---

## 18. Performance

The site should feel fast and technically well engineered.

Requirements:

- optimize images,
- lazy-load noncritical media,
- minimize JavaScript,
- avoid unnecessary dependencies,
- avoid blocking animations,
- use appropriate caching,
- and maintain strong Core Web Vitals.

Do not add a library when the same result can be achieved cleanly with existing tools or CSS.

Visual ambition should not come at the expense of performance.

---

## 19. Implementation Principles

Follow these principles throughout development:

1. Reuse existing components before creating new ones.
2. Keep components focused and understandable.
3. Avoid unnecessary abstractions.
4. Centralize design tokens.
5. Maintain consistent spacing and typography.
6. Use semantic names.
7. Separate content from presentation when practical.
8. Preserve accessibility during redesigns.
9. Add dependencies only when they provide clear value.
10. Test significant visual changes on multiple screen sizes.
11. Maintain clear Git history.
12. Do not rewrite working systems without a concrete reason.

---
